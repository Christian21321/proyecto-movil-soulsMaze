# ADR-006: Estado de UI con StateFlow y flujo de datos unidireccional (UDF)

## Contexto

La capa de UI de CardClash necesita exponer el estado de la partida (mano,
tablero, mana, turno, fase) de forma reactiva, consistente y sin estados
inconsistentes. Sin una estrategia clara, los componentes de UI pueden mutar el
estado desde multiples sitios, produciendo bugs dificiles de reproducir y
estados intermedios invalidos.

Ademas, el motor es inmutable (ADR-004) y devuelve nuevos snapshots; la UI debe
reaccionar a esos cambios de forma simple y confiable.

## Opciones consideradas

- **StateFlow con UDF (Unidirectional Data Flow)**: el estado de la UI se
  expone como un `StateFlow` inmutable. Los eventos del usuario se despachan
  como intenciones (acciones) que pasan por la capa de dominio/motor y producen
  un nuevo estado que fluye hacia la UI. Es la opcion adoptada.
- LiveData: patron estandar en Android, pero con posteo en hilos secundarios y
  menos seguro que StateFlow en corrutinas.
- State gestionado localmente en los composables (remember/saveable): util para
  estados locales, pero insuficiente para el estado global de partida.

## Decision

Se adopta **StateFlow + UDF** para el estado de la UI. El estado de la partida
se expone como un `StateFlow<MatchSnapshot>` (o una vista de UI del mismo)
inmutable y colectable con corrutinas. El flujo de datos es unidireccional: la
UI emite intenciones, la capa de presentacion las traduce en `CombatAction` del
motor, el motor devuelve un nuevo `MatchSnapshot`, y este se publica en el
`StateFlow` para que la UI se recompondra. Ninguna capa muta el estado fuera de
este canal.

## Consecuencias

- Estado siempre consistente: la UI solo observa el ultimo snapshot emitido.
- Facil de probar: se puede recolectar el flujo y verificar la secuencia de
  estados emitidos.
- La sincronizacion remota (ADR-007) encaja naturalmente: las acciones entrantes
  del rival se aplican al motor y el nuevo snapshot fluye por el mismo `StateFlow`.
- Requiere disciplina para no mutar el estado directamente desde la UI y para
  recolectar el flujo dentro del Scope de vida adecuado de la UI.
