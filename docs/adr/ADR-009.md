# ADR-009: Esquema Firestore para sincronizacion PvP (Etapa 4)

## Contexto

El modo PvP se sincroniza mediante Firebase Firestore con el patron de host
autoritativo (ADR-007). Para que la sincronizacion sea segura y correcta se
requiere un esquema bien definido que separe el estado completo (que solo debe
manejar el host) de una proyeccion filtrada que el cliente pueda ver, sin
revelar la mano del rival ni permitir manipulaciones.

El disenio debia resolver ademas la concurrencia (dos clientes accediendo a la
misma partida), la idempotencia ante reintentos y la reconciliacion si el host
pierde memoria.

## Opciones consideradas

- **Snapshot bifurcado `stateHost`/`stateClient` con cola de acciones**: el
  host conserva el estado completo en `stateHost` y publica una proyeccion
  filtrada en `stateClient`; las acciones viajan por una cola separada. Es el
  patron reconciliado y adoptado.
- Unico documento con el estado completo legible por ambos: mas simple, pero
  expone la mano y los mazos del rival, comprometiendo la partida.
- Estado calculado en el servidor (Cloud Functions): mas seguro, pero anade
  latencia y complejidad operativa sin necesidad para una 1v1 casual.

## Decision

Se adopta el esquema **bifurcado** con host autoritativo y cola de acciones.

### Patron general

El host ejecuta el motor local y publica el estado; el cliente solo envia
acciones y recibe snapshots. **Firestore es transporte, no autoridad**: la
legalidad de cada jugada la valida el motor en el host, nunca Firestore.

### Coleccion `matches/{matchId}` (metadata ligera)

Campos: `hostId`, `clientId`, `matchCode` (6 caracteres), `phase`
(`PREPARING`/`PLAYING`/`FINISHED`), `turn`, `currentPlayer`, `winner`, `status`
(`WAITING`/`ACTIVE`/`FINISHED`/`ABANDONED`), `createdAt`, `updatedAt`.

### Documento `matches/{matchId}/stateHost/current`

Legible y escribible **solo por el host**. Contiene el `MatchSnapshot` COMPLETO:
ambas manos, mazos (`decks`), `fullDecks`, `cardOf`, tableros (`boards`), manas
(`manas`), `playedCardLastTurn`, `turn`, `currentPlayer`, `phase`, `winner` y el
`log` truncado a 50 entradas. Incluye ademas `version` y `processedActionSeq`.
Es la **fuente autoritativa** para reconstruir la partida si el host pierde
memoria.

### Documento `matches/{matchId}/stateClient/current`

Escrito por el host, legible **solo por el cliente**. Proyeccion filtrada:
`boards`, `manas`, `playedCardLastTurn`, `turn`, `currentPlayer`, `phase`,
`winner`, `log`, `clientHand` (la mano del propio cliente) y
`numCardsInHostHand` (SOLO el conteo), mas `version`. **Nunca** contiene la mano
del host, ni `decks`, ni `cardOf`.

### Coleccion `matches/{matchId}/actions/{autoId}` (cola de acciones)

Campos: `playerId`, `actionType` (whitelist estricta: `BEGIN_TURN`, `PLAY_CARD`,
`END_TURN`, alineada 1:1 con `CombatAction` del motor), `payload`
(`{instanceId, targetUnitId?}` para `PLAY_CARD`), `sequence` (monotona del
cliente), `timestamp`, `status` (`PENDING`/`PROCESSED`/`REJECTED`) y `result`.

### Concurrencia

- El cliente mantiene una secuencia monotona (`nextActionSeq`).
- El host mantiene `nextExpectedActionSeq` y procesa una accion a la vez con su
  cola interna.
- Ambas particiones (`stateHost`/`stateClient`) comparten `version` para
  detectar escrituras concurrentes.
- Idempotencia: las acciones de secuencia ya procesada no se reaplican.
- La union del cliente se registra con una unica transaccion Firestore.

### Mapeo y serializacion

- En `stateHost` se serializa el `MatchSnapshot` completo.
- En `stateClient` se escribe la proyeccion filtrada.
- El `DiceRoller` NO se serializa: vive en memoria del host al construir el
  motor.

### Seguridad (reglas Firestore)

- `stateHost`: lectura/escritura solo para `hostId == auth.uid`.
- `stateClient`: escritura solo para `hostId == auth.uid`, lectura solo para
  `clientId == auth.uid`.
- `actions`: restringida. `playerId == auth.uid` (una accion solo de su autor) y
  `actionType` dentro de la whitelist (`BEGIN_TURN`, `PLAY_CARD`, `END_TURN`).
- La legalidad estrategica de la jugada (si tiene mano, mana, si es su turno,
  etc.) la valida el MOTOR en el host, no Firestore.

## Consecuencias

- La mano y los mazos del host nunca se exponen al cliente a traves del estado.
- Al ser el host la unica autoridad de reglas, el cliente no puede forzar
  resultados manipulando Firestore.
- Requiere que el host publique ambos documentos (`stateHost` y `stateClient`)
  tras cada procesamiento, con su `version` compartida.
- Si el host pierde memoria, puede reconstruir toda la partida desde
  `stateHost`, lo que refuerza la robustez.
- El esquema es mas complejo que un unico documento, pero necesario por
  seguridad; la complejidad se concentra en el host.
- La reconciliacion de la concurrencia (secuencia y versiones) debe
  implementarse cuidadosamente para evitar partidas corruptas o acciones
  perdidas.

## Actualizacion (2026-08-29)

Actualizado por [ADR-013](ADR-013.md):

- En `stateHost`, el campo `boards` fue sustituido por `heroHealth`,
  `heroMaxHealth`, `heroStatuses` y `passives`: el estado del avatar de cada
  jugador reemplaza a los tableros de unidades. La condicion de victoria
  derivada es vida del avatar a 0 (`OPPONENT_DEFEATED`).
- En `stateClient`, `boards` fue sustituido por los mismos campos de avatar
  filtrados (vida de ambos jugadores, estados y pasivas), manteniendo el
  secreto de la mano y los mazos del host (nunca se publican `decks` ni
  `cardOf` del host).
- El payload de `PLAY_CARD` cambio de `{instanceId, targetUnitId?}` a
  `{instanceId, targetPlayer?}`: el objetivo ahora es un `PlayerId` (el avatar),
  no una unidad.
- Referencia: [ADR-013](ADR-013.md).
