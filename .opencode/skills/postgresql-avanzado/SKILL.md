# PostgreSQL Avanzado — Skill para db-specialist

## 1. Diferencias clave H2 vs PostgreSQL que afectan migraciones

| Aspecto | H2 | PostgreSQL |
|---|---|---|
| **Tipos enteros** | `INT`, `BIGINT`, `SMALLINT`, `TINYINT` | `INTEGER`, `BIGINT`, `SMALLINT` (no `TINYINT`, usar `SMALLINT`) |
| **Serial / auto-increment** | `IDENTITY` o `AUTO_INCREMENT` | `SERIAL`, `BIGSERIAL`, o `IDENTITY` (SQL standard desde PG 10) |
| **Boolean** | `BOOLEAN` (acepta `TRUE`/`FALSE`/`UNKNOWN`) | `BOOLEAN` (solo `TRUE`/`FALSE`/`NULL`, sin `UNKNOWN`) |
| **Texto** | `VARCHAR`, `CLOB` | `VARCHAR` (sin limite = `VARCHAR`), `TEXT` (equivalente) |
| **JSON** | `JSON` (como string) | `JSON` y `JSONB` (binario, indexable con GIN) |
| **Secuencias** | `SEQUENCE` con sintaxis propia | `SEQUENCE` con `CREATE SEQUENCE`, `NEXTVAL('seq')` |
| **Funciones de fecha** | `CURRENT_DATE()`, `DATEADD()`, `DATEDIFF()` | `CURRENT_DATE`, `DATE + INTERVAL '1 day'`, `AGE()`, `EXTRACT()` |
| **Full-Text Search** | No nativo | `tsvector`/`tsquery`, `to_tsvector()`, `plainto_tsquery()` |
| **Particionamiento** | No nativo (tablas separadas + vistas) | `PARTITION BY RANGE/LIST/HASH` desde PG 10, mejorado en PG 12+ |
| **PL/pgSQL** | Sintaxis limitada, no compatible | `LANGUAGE plpgsql` con bloques `$$`, variables, cursores |
| **Indices** | B-tree, Hash | B-tree, Hash, GIN, GiST, BRIN, SP-GiST, Bloom |
| **Extensiones** | No | `CREATE EXTENSION`, ecosistema rico (PostGIS, pgvector, pgcrypto, etc.) |
| **Esquemas** | `PUBLIC` por defecto, sintaxis `SCHEMA` | `public` por defecto, `CREATE SCHEMA`, `search_path` |
| **Transactions DDL** | No | `CREATE TABLE` dentro de transacciones, `ROLLBACK` de DDL |

### Mapeo de tipos comunes POS app-comida

```sql
-- H2: IDENTITY
-- PG con SERIAL (legacy)
id INTEGER PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY;

-- PG moderno (SQL standard, recomendedo)
id INTEGER PRIMARY KEY GENERATED ALWAYS AS IDENTITY;

-- H2: DOUBLE
-- PG: DOUBLE PRECISION o NUMERIC(10,2) para montos
total NUMERIC(12,2) NOT NULL;

-- H2: TIMESTAMP
-- PG: TIMESTAMPTZ (with time zone) para evitar confusiones horarias
created_at TIMESTAMPTZ NOT NULL DEFAULT NOW();
```

## 2. Estrategia de migracion H2 -> PostgreSQL

### Opcion A: Alembic (FastAPI + SQLAlchemy)

1. Configurar dos `Engine` en SQLAlchemy (H2 y PG).
2. Generar migracion base con `alembic revision --autogenerate` apuntando a H2.
3. Ejecutar migracion en H2, extraer datos con `COPY` o script Python.
4. Ajustar migracion para PG (`sa.TEXT` en vez de `sa.String`, `sa.Boolean` con `sa.Boolean`, etc.).
5. Ejecutar `alembic upgrade head` contra PG vacia.
6. Cargar datos transformados.

```python
# Ejemplo de migracion Alembic para tipos
def upgrade():
    op.create_table(
        'products',
        sa.Column('id', sa.Integer(), autoincrement=True),
        sa.Column('name', sa.String(255), nullable=False),
        sa.Column('description', sa.Text(), nullable=True),  # antes CLOB
        sa.Column('price', sa.Numeric(12, 2), nullable=False),
        sa.Column('active', sa.Boolean(), default=True),
        sa.Column(  # JSONB para variantes
            'variants',
            postgresql.JSONB(astext_type=sa.Text()),
            nullable=True
        ),
        sa.Column(
            'search_vector',
            postgresql.TSVECTOR,  # indice GIN se crea aparte
            nullable=True
        ),
        sa.PrimaryKeyConstraint('id')
    )
    # Indice GIN sobre JSONB
    op.create_index('idx_products_variants', 'products',
                    ['variants'], postgresql_using='gin')
```

### Opcion B: Flyway (Spring Boot)

1. Migraciones SQL en `src/main/resources/db/migration/`.
2. Deshabilitar `spring.jpa.hibernate.ddl-auto` y usar Flyway puro.
3. Migracion `V1__init.sql` con DDL PostgreSQL nativo.
4. Scripts de transformacion de datos por lotes.

### Pipeline recomendado

```
[H2 production] --dump--> SQL transformado --> [PG staging] --> validacion --> [PG production]
```

1. Dump de H2 como SQL compatible.
2. Script Python/Perl que reescribe tipos y funciones.
3. Carga en staging PG con `psql`.
4. Validacion automatica (conteo de registros, checksums, integridad referencial).
5. Ventana de mantenimiento: detener app, migracion final, redireccion.

## 3. JSONB — Menus con variantes y personalizaciones

Tipico en POS: productos con variantes (tamano, ingredientes), personalizaciones (sin cebolla, extra queso).

```sql
-- Tabla de productos con JSONB para variantes
CREATE TABLE products (
    id          INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name        VARCHAR(255) NOT NULL,
    category_id INTEGER REFERENCES categories(id),
    base_price  NUMERIC(12,2) NOT NULL,
    variants    JSONB DEFAULT '[]'::jsonb,
    modifiers   JSONB DEFAULT '[]'::jsonb,
    created_at  TIMESTAMPTZ DEFAULT NOW()
);

-- Ejemplo de JSON en variants
[
  {
    "name": "Tamanio",
    "type": "single",           -- unica seleccion
    "options": [
      {"label": "Pequeno", "price_modifier": 0},
      {"label": "Grande", "price_modifier": 2.50}
    ]
  },
  {
    "name": "Ingredientes extra",
    "type": "multiple",          -- multiples selecciones
    "max": 3,
    "options": [
      {"label": "Queso extra", "price_modifier": 1.00},
      {"label": "Tocino", "price_modifier": 1.50},
      {"label": "Aguacate", "price_modifier": 1.00}
    ]
  }
]
```

### Consultas utiles con JSONB

```sql
-- Productos que tienen variante "Grande"
SELECT id, name
FROM products
WHERE variants @> '[{"options": [{"label": "Grande"}]}]';

-- Productos donde "Tocino" esta disponible como modifier
SELECT id, name
FROM products
WHERE modifiers @> '[{"options": [{"label": "Tocino"}]}]';

-- Extraer todas las opciones como filas
SELECT
    p.id,
    p.name,
    jsonb_array_elements(p.variants)->>'name' AS variant_name,
    jsonb_array_elements(
        jsonb_array_elements(p.variants)->'options'
    )->>'label' AS option_label
FROM products p
WHERE p.variants IS NOT NULL;
```

### Indice recomendado

```sql
CREATE INDEX idx_products_variants_gin ON products USING GIN (variants jsonb_path_ops);
```

`jsonb_path_ops` optimiza operadores `@>`, `?`, `?|`, `?&` y reduce tamano del indice ~40%.

## 4. Full-Text Search con tsvector/tsquery

Busqueda de productos por nombre, descripcion, categoria.

```sql
-- Agregar columna tsvector
ALTER TABLE products ADD COLUMN search_vector TSVECTOR;

-- Poblar con funcion concatenada (incluye nombre, descripcion, categoria)
CREATE FUNCTION products_search_update() RETURNS trigger AS $$
BEGIN
    NEW.search_vector :=
        setweight(to_tsvector('spanish', COALESCE(NEW.name, '')), 'A') ||
        setweight(to_tsvector('spanish', COALESCE(NEW.description, '')), 'B') ||
        setweight(to_tsvector('spanish', COALESCE(
            (SELECT c.name FROM categories c WHERE c.id = NEW.category_id), ''
        )), 'C');
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

-- Trigger para mantener actualizado
CREATE TRIGGER trg_products_search
    BEFORE INSERT OR UPDATE OF name, description, category_id
    ON products
    FOR EACH ROW
    EXECUTE FUNCTION products_search_update();

-- Indice GiST para busqueda rapida
CREATE INDEX idx_products_search ON products USING GIST (search_vector);

-- Consulta de busqueda
SELECT id, name, description,
       ts_rank(search_vector, query) AS rank
FROM products,
     plainto_tsquery('spanish', 'pizza queso') AS query
WHERE search_vector @@ query
ORDER BY rank DESC
LIMIT 20;

-- Busqueda con correccion de prefijo
SELECT id, name
FROM products
WHERE search_vector @@ to_tsquery('spanish', 'pizz:*');
```

## 5. PL/pgSQL — Funciones y triggers para auditoria

### Tabla de auditoria de ordenes

```sql
CREATE TABLE order_audit_log (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    order_id    INTEGER NOT NULL,
    action      VARCHAR(50) NOT NULL,  -- 'CREATED', 'UPDATED', 'PAID', 'CANCELLED', 'REFUNDED'
    old_data    JSONB,
    new_data    JSONB,
    changed_by  VARCHAR(100) NOT NULL DEFAULT CURRENT_USER,
    ip_address  INET,
    created_at  TIMESTAMPTZ DEFAULT NOW()
);

CREATE INDEX idx_audit_order_id ON order_audit_log(order_id);
CREATE INDEX idx_audit_created_at ON order_audit_log(created_at);
```

### Trigger function para auditoria

```sql
CREATE OR REPLACE FUNCTION audit_order_changes()
RETURNS trigger AS $$
DECLARE
    v_action VARCHAR(50);
    v_old_json JSONB;
    v_new_json JSONB;
BEGIN
    IF TG_OP = 'INSERT' THEN
        v_action := 'CREATED';
        v_new_json := to_jsonb(NEW);
        INSERT INTO order_audit_log(order_id, action, new_data, changed_by)
        VALUES (NEW.id, v_action, v_new_json, COALESCE(NEW.updated_by, CURRENT_USER));
        RETURN NEW;

    ELSIF TG_OP = 'UPDATE' THEN
        v_action := 'UPDATED';
        v_old_json := to_jsonb(OLD);
        v_new_json := to_jsonb(NEW);

        -- Detectar cambios especificos
        IF OLD.status IS DISTINCT FROM NEW.status THEN
            CASE NEW.status
                WHEN 'paid'     THEN v_action := 'PAID';
                WHEN 'cancelled' THEN v_action := 'CANCELLED';
                WHEN 'refunded'  THEN v_action := 'REFUNDED';
                ELSE v_action := 'STATUS_CHANGED';
            END CASE;
        END IF;

        INSERT INTO order_audit_log(order_id, action, old_data, new_data, changed_by)
        VALUES (NEW.id, v_action, v_old_json, v_new_json, COALESCE(NEW.updated_by, CURRENT_USER));
        RETURN NEW;

    ELSIF TG_OP = 'DELETE' THEN
        v_action := 'DELETED';
        v_old_json := to_jsonb(OLD);
        INSERT INTO order_audit_log(order_id, action, old_data, changed_by)
        VALUES (OLD.id, v_action, v_old_json, COALESCE(OLD.updated_by, CURRENT_USER));
        RETURN OLD;
    END IF;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_order_audit
    AFTER INSERT OR UPDATE OR DELETE ON orders
    FOR EACH ROW
    EXECUTE FUNCTION audit_order_changes();
```

### Cierre de caja — funcion atomica

```sql
CREATE OR REPLACE FUNCTION close_cash_register(
    p_register_id INTEGER,
    p_closed_by   VARCHAR(100)
)
RETURNS TABLE(
    register_id    INTEGER,
    opened_at      TIMESTAMPTZ,
    closed_at      TIMESTAMPTZ,
    expected_total NUMERIC(12,2),
    actual_total   NUMERIC(12,2),
    difference     NUMERIC(12,2)
) AS $$
DECLARE
    v_opened_at TIMESTAMPTZ;
    v_expected  NUMERIC(12,2);
BEGIN
    -- Obtener apertura activa
    SELECT co.opened_at INTO v_opened_at
    FROM cash_openings co
    WHERE co.register_id = p_register_id
      AND co.closed_at IS NULL
    FOR UPDATE;  -- bloqueo pesimista

    IF NOT FOUND THEN
        RAISE EXCEPTION 'No hay apertura activa para registro %', p_register_id;
    END IF;

    -- Sumar ordenes pagadas en este turno
    SELECT COALESCE(SUM(o.total), 0) INTO v_expected
    FROM orders o
    WHERE o.register_id = p_register_id
      AND o.created_at >= v_opened_at
      AND o.status IN ('paid', 'closed');

    -- Cerrar apertura
    UPDATE cash_openings
    SET closed_at = NOW(),
        closed_by = p_closed_by,
        expected_total = v_expected
    WHERE register_id = p_register_id
      AND closed_at IS NULL;

    -- Retornar resumen
    RETURN QUERY
    SELECT
        co.register_id,
        co.opened_at,
        co.closed_at,
        co.expected_total,
        co.actual_total,
        (co.actual_total - co.expected_total) AS difference
    FROM cash_openings co
    WHERE co.register_id = p_register_id
      AND co.closed_at IS NOT NULL
    ORDER BY co.closed_at DESC
    LIMIT 1;
END;
$$ LANGUAGE plpgsql;
```

## 6. Particionamiento de historicos de ordenes por mes

```sql
-- Tabla particionada
CREATE TABLE orders_history (
    id          BIGINT NOT NULL,
    store_id    INTEGER NOT NULL,
    register_id INTEGER NOT NULL,
    customer_id INTEGER,
    status      VARCHAR(20) NOT NULL,
    subtotal    NUMERIC(12,2) NOT NULL,
    tax         NUMERIC(12,2) NOT NULL DEFAULT 0,
    total       NUMERIC(12,2) NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL,
    closed_at   TIMESTAMPTZ,
    data        JSONB
) PARTITION BY RANGE (created_at);

-- Particiones mensuales
CREATE TABLE orders_history_2025_01 PARTITION OF orders_history
    FOR VALUES FROM ('2025-01-01') TO ('2025-02-01');

CREATE TABLE orders_history_2025_02 PARTITION OF orders_history
    FOR VALUES FROM ('2025-02-01') TO ('2025-03-01');

-- ... crear dinamicamente con funcion
CREATE OR REPLACE FUNCTION create_monthly_partition()
RETURNS void AS $$
DECLARE
    v_partition_name TEXT;
    v_start_date     TEXT;
    v_end_date       TEXT;
    v_next_month     DATE;
BEGIN
    v_next_month := date_trunc('month', NOW() + INTERVAL '1 month');
    v_partition_name := 'orders_history_' ||
                        to_char(v_next_month, 'YYYY_MM');
    v_start_date := to_char(v_next_month, 'YYYY-MM-DD');
    v_end_date := to_char(v_next_month + INTERVAL '1 month', 'YYYY-MM-DD');

    EXECUTE format(
        'CREATE TABLE IF NOT EXISTS %I PARTITION OF orders_history
         FOR VALUES FROM (%L) TO (%L)',
        v_partition_name, v_start_date, v_end_date
    );
END;
$$ LANGUAGE plpgsql;
```

### Indice BRIN para tablas temporales

```sql
-- BRIN es ideal para datos ordenados temporalmente
CREATE INDEX idx_orders_history_created_brin
    ON orders_history USING BRIN (created_at)
    WITH (pages_per_range = 32);
```

BRIN escanea solo rangos de paginas, mucho mas liviano que B-tree en tablas enormes.

## 7. pgvector — Busqueda semantica de productos

Para integracion futura con NLP/RAG: encontrar productos por similaridad semantica.

```sql
-- Habilitar extension
CREATE EXTENSION IF NOT EXISTS vector;

-- Tabla con embeddings
CREATE TABLE product_embeddings (
    product_id  INTEGER PRIMARY KEY REFERENCES products(id) ON DELETE CASCADE,
    embedding   VECTOR(384),  -- dimensiones segun modelo (ej. all-MiniLM-L6-v2)
    model_name  VARCHAR(100) NOT NULL DEFAULT 'all-MiniLM-L6-v2',
    updated_at  TIMESTAMPTZ DEFAULT NOW()
);

-- Indice IVFFlat (aproximado, mas rapido que exacto)
CREATE INDEX idx_product_embeddings_ivfflat
    ON product_embeddings
    USING ivfflat (embedding vector_cosine_ops)
    WITH (lists = 100);

-- Busqueda semantica (cosine distance)
SELECT
    p.id,
    p.name,
    p.base_price,
    1 - (pe.embedding <=> '[0.012, 0.045, ...]'::vector) AS similarity
FROM product_embeddings pe
JOIN products p ON p.id = pe.product_id
ORDER BY pe.embedding <=> '[0.012, 0.045, ...]'::vector
LIMIT 10;
```

### Pipeline de actualizacion

```python
# Pseudocodigo: job externo que genera embeddings
def update_product_embeddings():
    products = db.query("SELECT id, name, description, category FROM products")
    model = SentenceTransformer('all-MiniLM-L6-v2')
    for p in products:
        text = f"{p.name} {p.description} {p.category}"
        emb = model.encode(text).tolist()
        db.execute("""
            INSERT INTO product_embeddings (product_id, embedding)
            VALUES (%s, %s::vector)
            ON CONFLICT (product_id)
            DO UPDATE SET embedding = EXCLUDED.embedding, updated_at = NOW()
        """, (p.id, emb))
```

## 8. PostGIS — Geolocalizacion de sucursales

```sql
CREATE EXTENSION IF NOT EXISTS postgis;

CREATE TABLE branches (
    id          INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name        VARCHAR(255) NOT NULL,
    address     TEXT,
    phone       VARCHAR(20),
    location    GEOGRAPHY(Point, 4326),  -- WGS84 lon/lat
    delivery_radius_m NUMERIC(10,2) DEFAULT 5000,
    is_active   BOOLEAN DEFAULT TRUE
);

CREATE INDEX idx_branches_location ON branches USING GIST (location);

-- Sucursales mas cercanas a un punto
SELECT id, name,
       ST_Distance(location, ST_MakePoint(-99.1332, 19.4326)::geography) AS distance_m
FROM branches
WHERE ST_DWithin(location, ST_MakePoint(-99.1332, 19.4326)::geography, 5000)
ORDER BY distance_m;

-- Sucursales dentro de un poligono (zona de reparto)
SELECT id, name
FROM branches
WHERE ST_Within(
    location::geometry,
    ST_GeomFromText('POLYGON((-99.2 19.4, -99.1 19.4, -99.1 19.5, -99.2 19.5, -99.2 19.4))', 4326)
);
```

## 9. Indices: GIN, GiST, BRIN

| Tipo | Uso | Recomendado para |
|---|---|---|
| **GIN** (Generalized Inverted Index) | JSONB, arrays, tsvector | `jsonb_path_ops` para consultas `@>`, GIN en tsvector para FTS |
| **GiST** (Generalized Search Tree) | tsvector, geometrias, rangos | Busqueda de texto completo, datos geograficos (con PostGIS) |
| **BRIN** (Block Range INdex) | Datos correlacionados fisicamente | Tablas temporales (ordenes, auditoria), facturacion mensual |
| **B-tree** | Igualdad, rangos, ordenamiento | Claves primarias, columnas con alta cardinalidad |
| **Hash** | Igualdad exacta (obsoleto en PG 10+) | No recomendado, preferir B-tree |

### Ejemplos de creacion

```sql
-- GIN para JSONB (path ops)
CREATE INDEX idx_products_variants ON products USING GIN (variants jsonb_path_ops);

-- GIN para tsvector
CREATE INDEX idx_products_fts ON products USING GIN (search_vector);

-- GiST para tsvector (alternativa, mejor para ranking)
CREATE INDEX idx_products_fts_gist ON products USING GIST (search_vector);

-- BRIN para tabla de ordenes
CREATE INDEX idx_orders_created_brin ON orders USING BRIN (created_at) WITH (pages_per_range = 32);

-- Indice compuesto parcial
CREATE INDEX idx_orders_paid_date ON orders (created_at)
    WHERE status = 'paid';
```

## 10. Buenas practicas de rendimiento y modelado

### Modelado

- Preferir `NUMERIC(12,2)` sobre `FLOAT`/`DOUBLE PRECISION` para montos.
- Usar `TIMESTAMPTZ` siempre (nunca `TIMESTAMP` sin timezone).
- `GENERATED ALWAYS AS IDENTITY` en vez de `SERIAL` (SQL standard, evita huecos).
- Esquemas separados: `pos` (transaccional), `reporting` (vistas materializadas), `audit`.
- Vistas materializadas para reportes diarios, refrescar con `REFRESH MATERIALIZED VIEW CONCURRENTLY`.

### Consultas

- `EXPLAIN (ANALYZE, BUFFERS)` para diagnosticar.
- `LIMIT` + `OFFSET` con ordenamiento sobre columna indexada.
- Evitar `SELECT *`, siempre listar columnas.
- Usar `LATERAL` para subconsultas correlacionadas.
- Preferir `JSONB` sobre EAV (Entity-Attribute-Value) para datos flexibles.

### Configuracion PostgreSQL (postgresql.conf)

```ini
# Memoria compartida (25% de RAM)
shared_buffers = 2GB
effective_cache_size = 6GB
work_mem = 64MB          # por operacion de sorting/hash
maintenance_work_mem = 512MB

# Escritura
wal_buffers = 16MB
wal_level = replica
synchronous_commit = off  # si RPO lo permite

# Planificador
random_page_cost = 1.1    # SSD
effective_io_concurrency = 200

# Conexiones
max_connections = 50
```

### Anti-patrones a evitar

- **EAV** para variantes de productos: usar JSONB.
- **Tablas sin particionar** con millones de filas de ordenes: particionar por mes.
- **_Soft-deletes_ masivos**: usar tablas de archivado o particionamiento.
- **Triggers que hacen queries lentas**: mantenerlos ligeros, registrar solo cambios.
- **Secuencias con cache = 1**: usar `CACHE 100` en tablas de alto volumen.
